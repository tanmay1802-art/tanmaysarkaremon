Linux File Permissions Explained

Read, write and execute for owner, group and others, with chmod and chown.

By Tanmay Sarkar Emon · Published 12 Oct 2026 · Updated 13 Oct 2026 · 4 min read

This guide is for learning. Run these commands only on your own lab or servers.

Every file has an owner, a group and permissions for three kinds of users. Reading the output of ls -l is the first skill to learn.

ls -l notes.txt
-rw-r----- 1 student staff 120 notes.txt

The first block is the owner (rw-), then the group (r--), then everyone else (---). Read is 4, write is 2 and execute is 1.

Change permissions

chmod 640 notes.txt
chmod u+x script.sh

Change owner and group

sudo chown student:staff notes.txt

Good habits

Give the least access that works. Avoid chmod 777, because it lets every user on the system change the file.

Practise on test files in your home folder, not on system directories.

Reading the first column

In a line such as -rw-r----- the first character is the type: a dash is a normal file, d is a directory and l is a link. The next nine characters are three groups of three: owner, group and others. Each group shows r for read, w for write and x for execute, or a dash where the right is missing. Once you can read this fast, most permission problems become easy to diagnose.

The numbers

Read is 4, write is 2 and execute is 1, and you add them for each group. So 7 is full access, 6 is read and write, 5 is read and execute, 4 is read only and 0 is nothing. A mode of 640 gives the owner 6, the group 4 and others 0. A script usually needs 750 or 755, a private key needs 600 and a normal text file 644.

Directories behave differently

For a directory, read lets you list the names, write lets you create or delete entries and execute lets you enter it and reach the files inside. This is why a folder with 644 looks fine but you cannot open it, and why a file can be deleted by someone who cannot read it if they have write access to the folder. When a file is not accessible, check every folder on the path, not only the file.

namei -l /var/www/html/index.html

This command prints the permissions of each part of the path, so the blocked folder is easy to see.

Default permissions and umask

New files are not created with 666 or 777. The umask removes bits from those defaults. A umask of 022 gives files 644 and directories 755. A stricter 027 removes all access for others, which is a good choice on a shared server. Check yours with umask.

Special bits you will meet

The sticky bit on a shared folder like /tmp lets users delete only their own files. The setgid bit on a directory makes new files inherit the group, which helps in a team folder. The setuid bit on a program makes it run as its owner, which is powerful and risky, so finding unexpected setuid files is a normal security check.

find / -perm -4000 -type f 2>/dev/null
find /var/www -type f -perm -o+w 2>/dev/null

The second command lists files that anyone can write, which should usually be empty.

Recursive changes need care

Running chmod -R 755 on a whole folder makes every file executable, including text files. Set folders and files separately instead.

find site -type d -exec chmod 755 {} +
find site -type f -exec chmod 644 {} +

Also double check the path before you press Enter, because a recursive command on the wrong folder, especially with sudo, can break a system.

A practical example

For a web folder, make the web server user able to read the files but not edit them: owner is your deploy user, group is the web server group, files 640 or 644 and folders 750 or 755. Then only the deploy user can change the site, and a bug in the web application cannot overwrite it.

Practice in your own lab

Make a folder with three files, set 600, 640 and 644 on them, and read each one as a second user. Note which ones fail and why. Then remove the execute bit from the folder and see how the result changes. Writing a short table of mode, user and result is a quick way to make the rules stick before an exam or practical test.
